# NBP rates 227 — foreign-currency documents, stage 3 step 2 (23.10.2026)

## What it does
A document in a foreign currency gets the mid rate of NBP table A from the last table published
before its tax point (art. 31a ust. 1 ustawy o VAT), stored on the document when it is issued, with its
VAT and totals converted to PLN.

## Tables (own, migration `227_nbp_rates`)
- `nbp227_rates` (tenant, currency ≠ PLN, `effective_date`, `table_no` `NNN/A/NBP/YYYY` with the year of the date,
  `mid numeric(10,4)`, `covered_through`, `source` fetched|manual, `fetched_at`, actor/key). `covered_through` is
  the last day without a later table A, at most 31 days after the table.
- `nbp227_document_rates` (tenant, document → FK `documents`): currency, `tax_point` and its basis (sell_date |
  issue_date), `rate_date < tax_point`, table, mid, source, net/VAT/gross in the currency and in PLN, actor/key,
  `captured_with_issue`.
- `nbp227_document_rate_vat` (one row per VAT rate; FK on `(tenant, document, mid)` to the header, so every row uses the
  header's mid). A CHECK enforces `net_pln = round(net × mid)`, `vat_pln = round(vat × mid)` and `gross_pln = net_pln + vat_pln`.
- The two document tables are append-only: guard `nbp227_record_guard()` blocks update, delete and truncate, also for the owner.
  `dyna_app` may read and insert only. The rates table also allows update and delete, which only the app code uses.
- RLS `tenant_scope` applies to all three tables.
- Core tables get nothing except the internal RI triggers of the `documents` FK.

## Rules (`server/nbp227-model.ts`, pure)
- **Tax point** is the sell date. If the issue date is earlier than the sell date (invoice issued before delivery,
  art. 31a ust. 2), the issue date is the tax point instead.
- **Rate choice.** Take the latest stored table strictly before the tax point. It counts only if its
  `covered_through` reaches the day before the tax point.
  - Weekends, holidays (Christmas, 11 November) and business days without a table are covered by NBP data
    itself: the walk-back follows the last real publication, never a calendar.
  - Otherwise the issue is refused with a Polish reason. That covers no table, or no proof that no later table exists.
- **Coverage from a range read [start, end]:** each publication is covered up to the day before the next one.
  The last one is covered up to `end`, but never past yesterday in Warsaw, because today's table may still be published.
- **Manual rate** (admin only): the user gives the date, table, mid and "obowiązuje do". It is refused when:
  - an NBP-read table already exists on that date;
  - it overlaps a later stored table;
  - a range read proved there was no table that day;
  - the table number is already stored for another day.
- **NBP data overrides manual rates.** A later range read overrides manual rows on its dates and removes manual rows
  on days where NBP had no table.
- **Conversion:** each VAT rate is converted on its own, net and VAT each rounded half up to a grosz, gross = their sum.
  Document totals are the sums.

## Fetcher (`server/nbp227-fetch.ts`)
- Reads `GET https://api.nbp.pl/api/exchangerates/rates/a/{code}/{date}/?format=json` and `…/{start}/{end}/?format=json`
  through the declared provider transport (exact routes).
- Limits: 8 s timeout, 64 KiB.
- Strict schema: table A, the asked code, ascending dates inside the asked range.
- `mid` is kept as its JSON source text, with no float math and at most 4 decimals (otherwise `RATE_PRECISION`).
- A 404 "Brak danych" means no table in those dates.
- The ordinary NBP port gets `readTableA` only when both routes are declared; `--nbp-eur` declares them.
- Tests use recorded replies (`tests/nbp227-fixtures.ts`).
- One live smoke read on 23.10.2026 confirmed the reply shape: range 2026-10-09..22, day 2026-10-16, and Saturday 2026-10-17 → 404 text.

## Issue
- **No network while issuing.** The local `tax-issue` (`server/tax226-local-invoices.ts`) and Base `addInvoice`
  (`server/base-wire-invoices-runtime.ts`) never call NBP. In the issuing transaction:
  - after the 226 tax facts, `nbpRateBeforeNumberingInTx` checks that a proven stored rate exists for the tax point,
    before numbering (409 otherwise, no number consumed);
  - after `local_invoice_issue`, `captureDocumentNbpRateInTx` writes the record, before `SET CONSTRAINTS ALL IMMEDIATE`.
- **PLN invoices** cost no query and get no record.
- **Replays:** a replay keeps its record. A re-capture adds nothing.
- **Pinned files:** `local-invoices.ts`, `local-invoice-routes.ts` and `local-invoice-values.ts` are untouched,
  and the pins are asserted in `tests/nbp227-issue-hooks.test.ts`.
- **Today every issuing path is PLN-only.** The 157 frame refuses `currency <> 'PLN'` ("Niepoprawne pieniądze faktury"),
  and FA(3)/B2B 158/159 are PLN-only too. So the 227 hooks take effect with the first foreign-currency issue path.
  The DB test shows that refusal on a real EUR order. It writes the record through the same in-transaction functions,
  on a real EUR document row from the DEMO path.

## API / UI
- `GET /api/nbp227/rates?currency=EUR` (documents:read)
- `POST /api/nbp227/rates/fetch` with `{currency,start,end}` or `{currency,tax_point}` (the 14 days before it). Needs
  documents:write, admin or operator. Returns 503 without a reader, 502/504/429 with a Polish reason.
- `PUT /api/nbp227/rates/manual` (admin)
- `GET /api/nbp227/rate-for?currency&tax_point[&vat_minor]`: the stored rate or the refusal, plus the line
  "Kurs NBP z dnia …, tabela …, 1 EUR = … PLN; VAT w PLN: … zł"
- `GET /api/local-invoices/documents/:id/nbp`: the record, or "Faktura w PLN — przeliczenie kursem NBP nie dotyczy."
- `nbp227_available` in `/api/health`.
- UI: Dokumenty → Kursy NBP (stored rates, "Sprawdź kurs", "Pobierz z NBP", "Kurs ręczny"), and the NBP section in
  the local invoice detail.
