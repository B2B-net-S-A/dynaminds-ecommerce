# KSeF 229 — local KSeF 2.0 client, offline invoices and the KSeF queue, stage 3 step 4 (23.10.2026)

## What it does
- **Settings per seller NIP (Ustawienia → KSeF).** Environment, authentication by KSeF token or KSeF certificate, an optional KSeF certificate of type Offline (for KOD II), active flag. "Sprawdź połączenie" runs challenge → MF public keys → authentication → token redeem and shows every step.
- **Sending an issued document.** The file sent is exactly the FA(3) XML of `GET /api/fa3/documents/:id/fa3.xml` (local FV, B2B FV, consumer corrections 188 and 206/207, B2B corrections, and since migration 231 the FV-S invoices of 230). The app authenticates, opens an online session, encrypts the invoice, sends it, polls its status, downloads the UPO and closes the session. The KSeF number, status and UPO are stored with the document.
- **Offline invoices.** When KSeF answers 5xx, times out or cannot be reached, the invoice becomes an offline invoice (with its QR codes and deadline). The user can also choose offline24 or the emergency mode. "Kolejka KSeF" sends them later; the KSeF number is then stored on the same submission.
- **Corrections and JPK.** FA(3) KOR uses `NrKSeF=1` + `NrKSeFFaKorygowanej` when the corrected invoice has a stored KSeF number (else `NrKSeFN=1`, as before). JPK_V7 rows carry `NrKSeF`, `OFF` (offline, not yet numbered) or `BFK` (issued outside KSeF).
- **Fully local.** No call to any MF host. The test/demo/prod base URLs are constants in `server/ksef229-client.ts`, but `KSEF_REAL_ENABLED=false` makes the client refuse them before any request ("Połączenie z KSeF Ministerstwa Finansów jest wyłączone w tej lokalnej wersji"). The only server the app talks to is the local fake KSeF on a loopback address (`server/ksef229-fake.ts`).

## Tables (own, migration `229_ksef`, 14493 B, sha256 54dfc514…)
- **`ksef229_configs`** — per tenant and NIP: `environment` (local_fake|test|demo|prod), `base_url` (only for local_fake, loopback only, CHECK), `auth_method`, `secret_ciphertext` (the app's AES-256-GCM `encrypt()` of `{token}` or `{certificate_pem, private_key_pem}` plus the optional offline certificate), `secret_fingerprint` (HMAC of the secret with the installation key, 16 hex), certificate serials, `active`. Never deleted (deactivated); `tenant_id`, `nip`, `created_*` immutable.
- **`ksef229_sessions`** — online|batch, `opening → open|failed`, `open → closed|failed`, reference set once.
- **`ksef229_submissions`** — `document_kind` local_invoice | b2b_invoice | local_consumer_credit | consumer_return_credit | b2b_correction, and `invoice230` since 231 (24.10.2026: migration `231_ksef_invoice230` widens this one CHECK, same name, nothing else changes); one live submission per document (partial UNIQUE where `state<>'rejected'`); `xml` with CHECKed `xml_sha256` and `xml_bytes`; `issue_mode` online|offline24|offline|awaryjny with `offline_reason`, `offline_at`, `qr_invoice_url` (KOD I), `qr_certificate_url` (KOD II), `send_deadline`; KSeF `reference_number`, `status_code/description/details`, `ksef_number` (format CHECK, UNIQUE per tenant), `acquisition_at`, `upo_xml` (+ CHECKed sha256), attempts, last error, send lease.
  - Guard `ksef229_submission_guard()`: document, XML and hash never change; `queued → queued|sent|accepted|rejected`, `sent → sent|accepted|rejected`, accepted keeps everything but the UPO (set once), rejected is final; offline data set once (online → offline only while queued; the emergency deadline may be added once); reference and KSeF number set once. No DELETE/TRUNCATE, also for the owner.
- **`ksef229_events`** — append-only log (config, check, session_open/close, send, status, upo, offline, unavailable, refused, error) without secrets.
- RLS `tenant_scope`, `dyna_app` column grants (no DELETE anywhere). No foreign key to any core table: invoices and corrections live in several ledgers (`documents`, `local_consumer_credit_documents`, `return_credit206_documents`), so the document id is checked by the application through the FA(3) entry point. The FKs are submissions→sessions and events→submissions/sessions (own tables).
- Guards: all nine + `local_invoice_guards()` true before and after applying 229 in a transaction on a 218–228 clone, after real `migrate()` 218–229 on fresh clones 03 and 05, and after the DB test.

## KSeF 2.0 flow implemented (client `server/ksef229-client.ts`)
`POST /auth/challenge` → `GET /security/public-key-certificates` → token: `POST /auth/ksef-token` with RSA-OAEP-SHA256(`token|timestampMs`) / certificate: `POST /auth/xades-signature` → `GET /auth/{ref}` (100 → 200) → `POST /auth/token/redeem` → `POST /sessions/online` (`formCode FA (3) / 1-0E / FA`, AES-256 key RSA-OAEP-encrypted with the MF SymmetricKeyEncryption key, IV) → `POST /sessions/online/{ref}/invoices` (AES-256-CBC/PKCS#7, hashes and sizes of plain and encrypted file, `offlineMode`) → `GET /sessions/{ref}/invoices/{invRef}` polled with backoff → `GET /sessions/{ref}/invoices/ksef/{nr}/upo` → `POST /sessions/online/{ref}/close`. Crypto is isolated in `server/ksef229-crypto.ts`. Errors: 5xx/429-after-retry/timeout/connection → `KsefUnavailableError`; 4xx → `KsefRefusedError` with the KSeF code and description; secrets are redacted from every message.

## Offline rules implemented (`server/ksef229-model.ts`)
| Mode | When | Deadline the app stores |
|---|---|---|
| `offline24` (art. 106nda) | chosen by the user | next business day after the issue date (P_1) |
| `offline` (art. 106nh, KSeF unavailable) | automatic, when a send gets 5xx / timeout / no connection | next business day after the later of the issue date and the day the failure was detected (the app cannot know when MF ends the unavailability, so it never sets a later date than the law) |
| `awaryjny` (art. 106nf) | chosen by the user, with the end date from the MF announcement | 7 business days after that end; without the end date the deadline stays open and can be added once later |
- Business days: Monday–Friday except the public holidays of ustawa o dniach wolnych od pracy (Easter Sunday and Monday, Pentecost, Corpus Christi; 24 December from 2025).
- **KOD I** (invoice verification): `{qr host}/invoice/{seller NIP}/{P_1 as DD-MM-YYYY}/{SHA-256 of the stored file, base64url}`; label `OFFLINE` until the number exists, then the KSeF number.
- **KOD II** (issuer certificate): `{qr host}/certificate/Nip/{context NIP}/{seller NIP}/{offline certificate serial}/{hash}/{signature}`; the signature (RSA-PSS SHA-256 salt 32, or ECDSA P-256 IEEE-P1363) covers the URL without `https://`; label `CERTYFIKAT`. Only generated when an offline certificate is configured; otherwise the invoice shows "KOD II nie został wygenerowany".
- QR hosts: `qr-test|qr-demo|qr.ksef.mf.gov.pl`; for the local fake its own `/qr` pages (they show whether the invoice is known and verify KOD II).
- The offline file is stored at the moment it becomes offline and that exact file is sent later, so the KOD I hash stays valid.

## Reversible choices made
- No foreign key from submissions to `documents` (several ledgers); the id is validated by the FA(3) entry point.
- One live submission per document; a rejected one stays as history and a new send creates a new submission.
- The offline file is fixed when it becomes offline; the stored file, not a regenerated one, is sent later and offered as "plik wysłany do KSeF".
- `offline` deadline counted from the detection day (never later than the law).
- One online session per document send (also in "Wyślij wszystkie").
- Tokens are kept only in memory for one request; no access token is stored.
- Secret fingerprint = HMAC-SHA256 with the installation key (16 hex), so a changed secret is visible without showing it.
- The fake publishes SPKI keys (Node cannot mint X.509); the client accepts X.509 DER and SPKI.
- KSeF writes use `tenantTx` (two transactions per send: take, then result); the network flow runs outside any transaction. In the plain `buildApp` browser check a send took ~20–30 s because each `tenantTx` pays the preflights (see RODO228 doc).
- `ksef229_events` instead of `audit_events` for the KSeF trail; `audit_events` gets only `ksef.config_save` and `ksef.accepted` (no secrets).

## RES-04: no double send and no false rejection after a lost answer (26.10.2026, lane L1 part A, no migration)
**Bug.** Nothing durable was written before `sendInvoice`. When KSeF stored the invoice but its answer was lost (timeout, dropped connection, 5xx, or the process died before the result was stored), the next attempt opened a new session and sent the same file again. KSeF answered 440 "Duplikat faktury", and the app recorded the submission as **rejected**. The invoice had in fact been accepted and had a KSeF number.

**Fix.** It uses the existing 229 tables, guard and grants only: no migration, no change to `db.ts` or packaging.
- **Durable marker.** After the session opens and before `sendInvoice`, one transaction does three things. It stores the session (`ksef229_sessions`, state `open`, reference). It sets `session_id` on the still-`queued` submission (the guard allows this while queued). It appends the events `session_open` and `send` with the SHA-256 of the file. The write is fenced by this attempt's lease. If the lease was lost, nothing is sent and the session is closed. An uncertain send is therefore `state='queued' AND session_id IS NOT NULL AND reference_number IS NULL` (`sendUncertain()` in `ksef229-model.ts`).
- **Uncertain outcome.** When `sendInvoice` fails with `KsefUnavailableError`, the app first looks the file up by its SHA-256 in that session: `GET /sessions/{ref}/invoices`, paged by `x-continuation-token` (`KsefClient.findInvoiceByHash`).
  - If the file is found, it is polled, then accepted with its KSeF number and UPO, with no second POST.
  - If KSeF confirms the file is not in the session, the old offline rule applies.
  - If KSeF cannot be asked, the invoice becomes offline (KSeF is unavailable) and keeps the marker.
- **The next attempt** on a marked submission (user send, "Kolejka KSeF", "Sprawdź status" or the background job) reads first. It sends again only when the file is not in the marked session (HTTP 404 on an unknown session counts as not there).
- **440 "Duplikat".** The app reads the original's KSeF number and session reference from the status description and details (`duplicateOf()`). It confirms the original by the same SHA-256 in that session, then stores that number, the reference, the session (recorded when the app did not know it) and the UPO. The audit entry `ksef.accepted` gets `reconciled: true`. An unconfirmed 440 (no session named, or a different file with the same number) is **never rejected and never resent**: the submission stays `queued`/`sent` with the message "sprawdź ją w aplikacji KSeF".
- **Lease vs worst-case attempt** (security review stage 3, item 7):
  - The client has an overall deadline. Every request and wait is cut at `KSEF_ATTEMPT_BUDGET_MS` = 110 s, and no request starts after it.
  - The lease is `KSEF_LEASE_SECONDS` = 240 s, longer than the budget plus 60 s for the two transactions. The budget is also under the 2-minute job reaper of `tick()`.
  - Storing the result is fenced by the exact lease value, so a stale attempt cannot overwrite a newer one.
- **Token refresh.** An expired access token is renewed with `POST /auth/token/refresh` (refresh token, its `validUntil` − 60 s). A full login happens only when there is no refresh token or KSeF refuses the refresh.
- **Background status job `ksef.status`** (`server/ksef229-jobs.ts`; one dispatch branch in `server/worker.ts`; the existing `jobs` table, kind is free text, no schema change):
  - It is queued, at most one pending per submission, in the same transaction as a result that leaves the invoice `sent` or uncertain-with-KSeF-unreachable. It runs 1 minute later.
  - The job only reads (`reconcileDocument`, never sends). A queued invoice that was never handed over is not touched.
  - While KSeF still processes the invoice, or cannot be asked, the job throws a `Problem`, and the generic retry of `tick()` reads again with backoff up to `max_attempts`. An unconfirmed 440 ends the job.
- **Fake KSeF** (test infrastructure):
  - `loseNextResponse(route, 'drop'|'hang')` lets the request take full effect and then loses its answer.
  - It serves `GET /sessions/{ref}/invoices` with hashes and paging, and `POST /auth/token/refresh`.
  - The 440 details name the original number and session.
