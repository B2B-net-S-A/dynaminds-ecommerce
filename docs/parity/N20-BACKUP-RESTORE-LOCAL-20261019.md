# N20 — lokalny backup i odtworzenie

**PASS: rzeczywisty backup i odtworzenie DB/konfiguracji/obrazu oraz zachowanie niepustej kolejki. Podgląd aplikacji: PARTIAL.** Pełny Goal pozostaje OPEN.

Root użył istniejącego developerskiego `tools/local/backup-operator.mjs` i `server/recovery.ts`; ten CLI nie jest modułem uruchomionego pakietu N20.

Odczyt źródła używał wspólnego eksportowanego snapshotu RRRO i `pg_dump`; zapisano zaszyfrowany AES-256-GCM artefakt 14 110 756 B o SHA256 `8cdf1f53b33026b92a9547280d27acfb0b437253dcd2345a54d9922d9cd72531`, obejmujący 644 tabele i 1 obraz. Root odtworzył kopię na PG04, port 57084, w nowej bazie `dynaminds_restore_f45a5f0ea586bd73`; proces zakończył się EXIT0 po 21 978 ms. Oddzielny selection, pusty katalog i niepowtarzalny guard ograniczały wykonanie do jednej nowej kopii. Źródłowa baza PG03 nie była celem `pg_restore`. Wynik potwierdza zgodność fingerprintów wierszy i schematu v4, 646 zapisów ACL, 139 sprawdzeń zaszyfrowanych rekordów oraz 2 prywatne tabele z 13 343 wierszami i ich ACL. Odtworzony obraz ma 183 805 B i pełny SHA256 zgodny ze źródłem. FILE review sprawdził wynik, dokładny roster i liczniki manifestu oraz fizyczne bajty obrazu, bez publikacji konfiguracji lub klucza.

`manifest.tables` używa liczby rekordów i dwóch sum fragmentów MD5 wierszy; odrębne porównanie pełnych SHA256 powyżej zamyka mocniejszy warunek zgodności ze snapshotem N20. Nie uruchamiano odtworzonych 597 pending zadań. Ustawienia `preview_only:true` i `worker_enabled:false` w wyniku odtworzenia nie dowodzą uruchomienia zwykłego UI/API odtworzonej aplikacji.

Chrome firmy A zalogował się i pokazał płatne zamówienie oraz płatność. API potwierdziło health, własne `auth/me` i pełny odczyt zamówienia (trzy odpowiedzi 200); kolejny odczyt inventory zakończył się limitem HTTP 9s bez ACK i bez ponowienia. Wcześniejsza próba z błędną nazwą cookie zachowała 401 i zero zapisów biznesowych. Osobne żądania `POST /api/inventory/adjust` i `GET /api/inpost/points?query=Warszawa` otrzymały 423. UI nadal udostępniało przyciski operacji zapisujących; wystąpił także błąd 500 odczytu statusu. Dlatego pełny odbiór podglądu nie jest zamknięty.

Wyniki wskazują koszt użycia ścieżki transakcji zapisującej dla tych odczytów i nie dowodzą uszkodzenia restore. Nie ustalają samodzielnie dokładnej przyczyny wcześniejszego 500. Limity SQL 8s/klienta 9s nie zostały podniesione; limit HTTP 30s dotyczył wyłącznie tej diagnostyki. Poprawka dwóch GET do `tenantReadTx` wymaga kolejnego wydania i rzeczywistego odbioru.
